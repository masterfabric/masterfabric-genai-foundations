# 0001. llama.cpp serves the lab; vLLM is a chart option for GPU nodes

- Status: Accepted
- Date: 2026-11-21

## Context

The target platform serves open-weight models on-prem with vLLM on NVIDIA GPUs. The lab runs on an
Apple M4 Pro, where Docker runs in a Linux VM with **no GPU access**. Metal cannot be passed into the
VM, and vLLM's supported accelerators are CUDA, ROCm, TPU and others, with a CPU backend that targets
x86 and is not meant for production.

## Options

| Option | For | Against |
|---|---|---|
| vLLM CPU build in the cluster | Same server as production | Slow, heavy image, not representative of GPU behaviour |
| Ollama on the host (Metal) | Fast on Apple Silicon | Runs outside Kubernetes; breaks the "everything from one chart" story |
| **llama.cpp server in the cluster** | OpenAI-compatible API like vLLM (`/v1/chat/completions`, `/v1/embeddings`), continuous batching over parallel slots, GGUF quantisation, small arm64 image, Prometheus `/metrics` | CPU-only in the VM; not PagedAttention |

## Decision

The chart has `llm.backend: llamacpp | vllm`. The lab uses llama.cpp (`server-b12464`) with
Qwen2.5-1.5B-Instruct Q4_K_M, 4 parallel slots and an 8192-token shared context. The same image serves
bge-small-en-v1.5 embeddings. `values-vllm-gpu.yaml` switches to `vllm/vllm-openai` with a GPU
request, node selector and tolerations. The RAG API only talks to the OpenAI API, so it needs no change.

## Consequences

- The vLLM path is rendered and linted (`make lint`) but **not run** here. Throughput numbers in this
  repo are CPU numbers and say nothing about GPU serving. masterfabric-llm-serving-bench measures that
  separately.
# 0002. pgvector instead of Milvus for the retrieval store

- Status: Accepted
- Date: 2026-11-21

## Context

The corpus is small (207 chunks), and the platform team already runs PostgreSQL.

## Options

| Option | For | Against |
|---|---|---|
| **PostgreSQL 16 + pgvector (HNSW, cosine)** | One familiar database, SQL filters next to vectors, backups and RBAC already solved | Single node; not built for billions of vectors |
| Milvus | Scales out, GPU indexes | Etcd, MinIO/S3, Pulsar or Kafka, several services: heavy for a laptop and for this corpus size |
| In-process FAISS | Fastest to start | No persistence, no concurrent writers, no access control |

## Decision

pgvector runs as a StatefulSet with a PVC and a generated password that is kept across upgrades. One
`chunks` table stores source, section, content, a `trust` label and a `vector(384)` with an HNSW index.

## Consequences

- Measured retrieval takes milliseconds per question (see `timings_ms.retrieve` in the evaluation output).
- The `trust` column is what a row-level filter needs (for example, excluding `untrusted` sources for
  some users). Fine-grained access is the topic of masterfabric-secure-data-ai.
# 0003. Deterministic guardrails first, measured against evasions

- Status: Accepted
- Date: 2026-11-21

## Decision

Rules in `rag/app/guardrails.py`, applied at three points:

1. **Input**: block injection, extraction, jailbreak, delimiter, encoded-payload and exfiltration
   patterns. Mask Turkish PII: TCKN and IBAN (with checksums), +90 mobile numbers, email, and
   Luhn-valid cards.
2. **Context**: drop retrieved chunks that contain instructions aimed at the model.
3. **Output**: withhold answers that contain a per-process canary from the system prompt, redact PII,
   and flag missing or out-of-range citations.

Every event has a rule name, and each one is returned to the caller and counted in Prometheus.

## Why not only a classifier model

Rules are explainable, need no GPU and add microseconds. They also miss paraphrases, and the
evaluation includes 4 deliberate evasions to show that (0/4 caught). The canary and the "answer only
from context" prompt are the second layer. A model-based classifier (for example Llama Guard or a
fine-tuned small encoder) is the next layer, listed in the roadmap.
# 0004. One Helm chart, models fetched into PVCs, NetworkPolicies by label

- Status: Accepted
- Date: 2026-11-21

## Decision

- One chart (`charts/onprem-llm`) installs both model servers, pgvector, the API, the ingest Job and
  the ingress, so an environment is one `helm upgrade --install` with a values file.
- Model weights are not baked into images. An initContainer downloads each GGUF once into a PVC; the
  URL can point at an internal mirror (Artifactory or Nexus) for air-gapped sites, and an optional
  `sha256` pins the file.
- Only pods labelled `onprem-llm/model-client=true` (the API, the ingest Job and the load-test pod) can
  reach the model servers and the database. The ingress exposes only the API.
- The ingest Job is a post-install/upgrade hook. Readiness does not depend on it, which avoids a
  deadlock with `helm --wait` that the build actually hit.

# 0001. Benchmark servers that run here; no borrowed numbers

- Status: Accepted
- Date: 2026-11-21

## Context

The brief asks for throughput, latency, quantization and KV-cache effects on servers that actually
run. Tailscale machines may be used **read-only**, without changing their services.

## What was available (checked with `tailscale status`, 2026-11-21)

- The M4 Pro itself (14 cores, 24 GB) is the only online machine in the tailnet. Every other node
  (Mac Studio, Mac mini, the other MacBooks, iOS devices) was offline, last seen between 1 and 74
  days earlier. No remote server was benchmarked, and none was contacted.
- Ollama is installed on the host but was not running. It was **not started**: this repo does not
  start or change long-lived services on the machine.
- No NVIDIA GPU, so vLLM could not be run (see masterfabric-onprem-llm-stack ADR 0001).

## Decision

Benchmark the same llama.cpp server code, with the same GGUF files, on the two execution paths that
exist on this machine:

1. **Metal**: Homebrew `llama-server` (build 12359) on the host, all layers offloaded to the Apple GPU.
2. **CPU in a container**: `ghcr.io/ggml-org/llama.cpp:server-b12464` in the Colima VM (6 vCPU), which
   is how the k3d stack in masterfabric-onprem-llm-stack runs.

Both expose the OpenAI API, so the load generator would run unchanged against vLLM, and the
results tables have the same columns a vLLM run would fill.

## Consequences

- Results compare hardware paths and settings for one model family (Qwen2.5-1.5B-Instruct), not servers
  from different vendors.
- The two builds differ slightly (12359 vs 12464). Both are recorded.
# 0002. Methodology: streaming client, fixed output length, cold prompts

- Status: Accepted
- Date: 2026-11-21

## Decision

- **Streaming requests** to `/v1/chat/completions`. The client timestamps every content delta, which
  gives TTFT (time to the first token), inter-token latency (median gap per request) and end-to-end
  latency.
- **Fixed output length.** `ignore_eos` makes every request generate exactly `max_tokens` (128), so
  tokens/s compare like with like. Greedy decoding (temperature 0).
- **Fixed request counts.** Each concurrency level runs max(8, 3 × concurrency) requests with N in
  flight, after one unrecorded warm-up request.
- **4 server slots, 16k context** (`-np 4 -c 16384`) for the concurrency sweep. Prefill and KV tests
  use a 32k context, 8k per slot.
- **Cold prompts for prefill.** Long prompts are cut from real documentation with a different offset
  per request, and sent with `cache_prompt: false`. Prompt-cache reuse is measured separately, with a
  fresh server for each mode.
- **Quality of a quantization**: `llama-perplexity` on the same 38 KB documentation text, context 512,
  for every GGUF file.

## Not controlled

Other apps on the laptop, thermal state, and the download that ran in the background during the
first runs. Each configuration ran once; there are no confidence intervals beyond the perplexity error.
# 0003. Serving defaults: weight and KV quantization, slots, prompt cache

- Status: Accepted (for this lab's hardware; re-measure on new hardware)
- Date: 2026-11-21

## Context

The on-prem stack (masterfabric-onprem-llm-stack) shipped with Q4_K_M weights, an f16 KV cache,
4 slots and the prompt cache on, without measurements behind those choices. This repo measured them.

## Evidence (results/*.json)

| Question | Measurement | Result |
|---|---|---|
| Q4_K_M or Q8_0 weights? | perplexity, 38 KB lab docs, ctx 512 | 24.69 ± 1.09 vs 23.63 ± 1.04 (F16: 23.62 ± 1.04), within the error bars; file 1,066 vs 1,807 MiB (F16 3,396) |
| | Metal throughput, 4 concurrent | 381 vs 358 tok/s |
| | CPU container throughput, 4 concurrent | 184 vs 328 tok/s (reproduced: 181 vs 335) |
| f16 or q8_0 KV cache? | 32k context, 4 × ~5.5k-token prompts, Metal | KV buffer 896 vs 476 MiB (computed), server RSS 2,746 vs 2,042 MiB, 38.2 vs 37.9 tok/s |
| How many concurrent requests per replica? | 1-8 concurrent, 4 slots | throughput peaks at 4; at 8, TTFT p50 jumps from ~14 ms to ~1.5 s (queueing) |
| Prompt cache on? | 4k-token prompt sent twice | 1.89 s TTFT cold, 13 ms on the repeat with cache; no cost on the cold request |

## Decision

- **GPU/Metal nodes: Q4_K_M weights.** Slightly faster than Q8_0 and 41% smaller, with no
  measurable perplexity loss on our text.
- **CPU-only nodes: Q8_0 weights.** Counter-intuitive but measured twice: on this ARM CPU build Q8_0
  decodes batched requests much faster than Q4_K_M (11.7 vs 20.7 ms per token at 4 concurrent). The
  extra 740 MiB of RAM is cheap compared with the throughput gain. Re-measure on x86 nodes before
  copying this decision.
- **KV cache q8_0 with flash attention** when long contexts are needed: half the KV memory at the
  same decode speed. Keep f16 for short contexts, where the KV buffer is small anyway.
- **Concurrency = slots.** Size the replica count so steady-state concurrency per replica stays at
  or below the slot count; above it, requests wait for a free slot and TTFT becomes seconds.
- **Prompt cache on** (llama.cpp default). It is free for cold requests and removes prefill for
  repeated system prompts and RAG templates.

## Consequences

- The on-prem stack's Helm values keep Q4_K_M as the default; a CPU-node values file should switch
  to Q8_0. That change belongs in that repository and is not made here.
- Perplexity on 38 KB of text is a coarse quality signal. Task-level evaluation (masterfabric-onprem-llm-stack
  `eval/`) should be re-run before a quantization change goes to production.

# 0001. Synthetic personal data only, with checksum-valid identifiers

- Status: Accepted
- Date: 2026-11-21

## Context

KVKK (Law No. 6698) treats national ID numbers, IBANs, contact details and similar fields as personal
data. A public portfolio repository must never contain data about real people, yet detectors and
masks are only meaningful if they are tested on realistic formats.

## Decision

- All people are generated by `sdai/synth.py` from a fixed seed: random combinations of common first
  names and surnames, random cities and dates.
- TCKN and TR IBAN numbers are random digits **with valid checksums**; they are not issued to anyone.
  Card numbers use the 9-prefix, which no card network issues. E-mails use the reserved `example.com`
  domain. Phone numbers are random +90 5xx numbers.
- Generated datasets live in memory or under the git-ignored `data/` directory. Only small samples,
  needed to show what a role sees, appear in `results/`.

## Consequences

- Recall of 1.0 in the PII evaluation reflects template-generated notes; real free text is messier
  (see README limitations).
- A random 11-digit number passes the TCKN checksum about 1 time in 100, and a random 16-digit number
  passes Luhn 1 time in 10. Those collisions are what the precision numbers measure.
# 0002. Enforce column and row policies with secure views and a query check

- Status: Accepted
- Date: 2026-11-21

## Context

Apache Ranger (Cloudera SDX) enforces column masking and row filtering inside Hive/Impala, and
audits every access. This lab needs the same behaviour on a laptop, without a Hadoop stack.

## Options

1. Materialise a masked copy per role. Simple, but copies multiply and go stale.
2. **Secure views per role plus a pre-execution check.** One copy of the data; masks and filters
   are applied at query time, like Ranger.
3. Rewrite every user query. Powerful, but a custom SQL rewriter is a large attack surface.

## Decision

Option 2 on DuckDB:

- A YAML policy lists, per role, the visible columns with a mask each (default deny) and an optional
  row filter. One view per role is generated from it.
- Before execution, the SQL is parsed by DuckDB (`json_serialize_sql`). Only a single SELECT is
  accepted, with no table functions, and every referenced table must be the role's own view.
- External file access and configuration are locked after loading.
- The pseudonymisation key lives in a Python UDF, so a view definition never contains it.
- Every attempt, allowed or denied, goes to an audit log.

## Consequences

- 10 bypass patterns × 5 roles: 0 allowed (results/policy_eval.json).
- Masks cost nothing on aggregates; HMAC pseudonyms make full scans ~2.7× slower.
- In production, Ranger or Unity Catalog does this inside the engine. This code shows the policy model,
  not a replacement for an in-engine enforcement point.
# 0003. RAG: mask at ingest, filter before ranking; LLM guardrails are deterministic

- Status: Accepted
- Date: 2026-11-21

## Decision

- **Mask PII at ingest**, not at answer time. The index never holds identifiers, so no retrieval bug or
  prompt can expose them. Pseudonyms (HMAC) keep tickets about the same customer linkable.
- **Filter by ACL before ranking.** Post-filtering top-k avoids leaks too, but measured on 300
  queries it left the Istanbul desk with 0.32 of 5 results; pre-filtering returned 4.06 of 5.
- **Guardrails are deterministic and pattern-based**, one control per OWASP LLM Top 10 (2025) risk,
  each with a unit test. They are measured against a real model, including the attacks they miss.

## Evidence

| Risk | Baseline | Guarded |
|---|---|---|
| LLM01 direct injection | 7/10 succeeded | 4/10 (all paraphrases without trigger phrases) |
| LLM01 indirect (poisoned document) | 0/8 | 0/8 |
| LLM02 PII disclosure | 6/8 | 0/8 |
| LLM07 system prompt leak | 2/8 | 0/8 |
| Benign questions blocked | 0/10 | 0/10 |

## Consequences

- Patterns do not stop paraphrased injections. Production needs a trained classifier (for example
  Llama Guard or Prompt Guard) in addition, and should treat these patterns as a first layer.
- The model never followed the `[ID]` citation format, so the LLM09 grounding check would refuse
  every answer. A larger model or constrained output is needed before enabling it.
